# 逆向过程

记录关键判断、走过的弯路和最后怎么纠正的。失败路径往往比结论更有信息量。

## 起点

目标设备是 Fuji Xerox DocuCentre S2011：没有 PCL/PS 选项，只有 Windows 驱动，
需要让它从一块 ARM 单板（aarch64，2 GB 内存）直接出纸。两条路——换机器，或者自己实现它的页面语言。
选了后者。

`FFHBLALK-1.DLL` / `FFHBLACZR.DLL` 是驱动的核心；`.logproxy.dll` 负责与打印子系统对接。
静态反汇编能看结构，但格式细节还得靠**真实作业样本**对撞：把驱动指向文件端口，逐次捕获
不同内容的打印流，形成 `corpus/`（89 个受控样本：空白页、单字符、条纹、不同长度/位置的填充块……）。

## 弯路：以为是自研位流

页数据前面有 20 字节的「页设置记录」，后面是一段高熵二进制。最初按**自研算术编码位流**
去逆向，还真的「解」出了一套结构：`[17 字节 0][u 字节 0][16 位宽度][21 位尾]`，
在空白页 + 一个点的样本上完全自洽。

问题在于：这个「解码器」只对极空的页面成立。稍微复杂一点的样本立刻对不上。
现在回看，那只是某个固定前缀 + 大量零字节在任意模型下都会呈现的假象——
**用能拟合的数据结构去解释噪声，一定会"成功"**。

## 转折：一行 include

`foo2zjs` 项目里有个 `foo2hbpl2.c`，处理另一种 HBPL 打印机。它 `#include <jbig.h>`。

顺着这条线索重新看那 20 字节：

```
DL(4) D(1) P(1) XD(4) YD(4) L0(4) MX(1) MY(1)
        └── XD = 7040, YD = 4961 ──┘
```

标准 JBIG1 的 BIH 头。`XD = 7040` 是页高像素、`YD = 4961` 是页宽像素——
**JBIG 的一行等于页面的一列**。此前所有「纵向便宜、横向每行跳 7040」的怪现象一次性解释通了。

用 `jbigtopbm` 解一页，再做一次逆变换，纸面视图上的英文清楚可读。至此格式确定：
不是自研位流，是标准 JBIG1 压缩的**转置**位图。

## 自研编码与驱动对齐

用 `pbmtojbg` 编码同一张位图，与驱动页数据对比：**只差 1 字节**（偏移 16，jbigkit 写 `0x08`，
驱动写 `0x00`）。补上这一行 patch 后 `cmp` 完全相同。

这一步的意义：从此不必猜打印机「大概能接受」，编码结果与官方驱动字节级一致。

## 坐标映射怎么来的

在固定位置画单像素/小块，打出 8 组受控样本，比较码流里置位的位置，反推出：

```
JBIG 行 = 页面 x
JBIG 列 = 7015 − 页面 y     （等价于 GDI 坐标的 6918 − y_gdi，原点在纸面 97,97）
```

`tools/view.py` 用逆变换渲染成 PNG，方向与位置可以目视核对——这比任何推理都可靠。

## 三个实打实的 bug

| 现象 | 根因 | 修正 |
|---|---|---|
| 自编码页出现等距竖条纹 | 转置时把位下标写成了字节偏移（`y*rb + r` 应为 `y*rb*8 + r`） | 加 `*8` |
| 两页合并的作业只出第一张 | 每页都补了 `SD C1 A1 00 42`，第二个 `0x42` 被当作流结束 | `0x42` 只在整条流末尾发一次 |
| 双面时 PAGEINFO 数量对但打出来错乱 | 复制插入点取在行中间 | 改到 `PAGEINFO` 行末（`\n` 后）插入 |

第一条是最典型的「差一个 /8」——图案规则得像是打印机问题，实际是自己的位运算。

## 多页与双面

`hbpldecode.c` 里 `parse1()` 遇到 `0x42` 直接 `return`，说明它是**流**结束而非页结束。
用四个变体（完整 / 无 `0x42` / 只留 `SD C1 A1 00` / 全去掉）实打，只有「无 `0x42`」的变体
一次出两张纸，`prtMarkerLifeCount` +2 精确验证。

双面的三个标记是从 `FFHBLALK-1.DLL` 的字符串池里挖出来的：
`@PJL SET DUPLEX=`（OFF/ON）、`DUPLEXTYPE=`（SIMPLEX/DUPLEX/TUMBLE）、
`PAGEINFO=…DUPLEX[…]`（同三值）。三处必须一致，另外 `PHYSICALPAGES` / `LOGICALPAGES` /
`ESTIMATEDSHEETS` 与 `PAGEINFO` 条数要跟着改。

35 页双面实打：18 张纸、面数计数 +35，前后一致。

## 性能

一开始整本 35 页要 8 分钟以上。逐环节掐表后定位到三处（详见 [performance.md](performance.md)）：
gs 的分带渲染、串行编码、以及每 4 页一个作业边界导致的引擎停顿。三处改完 93.9 s 编码完，
总时长压到 2.6–3 分钟，瓶颈回归打印机引擎本身（4.4 s/面）。

## 方法论小结

1. **样本对撞优先于静态分析**：格式细节几乎都是从「改一个像素，看码流变哪几位」得到的。
2. **先找同族实现**：一行 `#include <jbig.h>` 省掉了几周的算术解码器逆向。
3. **等价性要字节级**：`cmp` 相同才算理解；「打出来像」不算。
4. **怀疑自己多于怀疑设备**：竖条纹、只出一张纸，最后都是自己代码里的错。
